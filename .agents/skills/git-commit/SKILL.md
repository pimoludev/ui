# git-commit

## Activation
Use when the user asks to commit, "préparer un commit", or write a commit message.
Do NOT use when the user only asks to review diffs or explain changes.

## Responsibilities
- Commit only the intended changes, verified against the repo's own validations.
- Never hide a failing check; never bypass hooks.

## Steps
1. Inspect the working tree: `git status`, `git diff`, `git diff --staged`, `git log --oneline -5`.
2. Identify the exact files that belong to this change.
3. Stage explicitly by path. **Never** `git add .` / `git add -A`.
4. Detect unresolved conflicts (`<<<<<<<`, `=======`, `>>>>>>>`), sensitive files (`.env*`, keys, credentials, tokens), and unintended generated/`dist/` files.
5. Run validations with `test-runner` at pre-commit scope: `pnpm verify:quick`.
   Add targeted skills when relevant: `public-api-review` (API change),
   `theme-integrity-audit` (tokens/themes/presets/CSS), `playground-sync` (new/changed component).
6. Run `test-coverage-audit` to flag mandatory untested scenarios for the change.
7. Confirm lint, TypeScript, formatting, build and any applicable control pass.
8. A component, prop, variant, state or placement change is **not committed** without its playground page update in the same commit (`playground-sync`): each new capability needs a demo a human can click, not a description. Documentation changes follow `documentation-sync`. Do not defer a demo to a follow-up.
9. **Stop** on any mandatory failure. Do not commit a red tree.
10. Write a message that records the changes actually made — facts about the commit, never a task list.

## Message format (mandatory)
```
type(scope): English description

EN:
- <what changed, area by area, with the affected paths>
- <the effect on behaviour or on the public API, when there is one>
- <what a reviewer needs to know to follow the change>

FR:
- <the same facts, in French>
```
- Types: `feat`, `fix`, `refactor`, `docs`, `test`, `style`, `perf`, `build`, `ci`, `chore`.
- Scope: package or area, e.g. `button`, `react`, `themes`, `design-tokens`, `playground`, `ci`.
- Conventional Commits: breaking change with `!` after the type/scope and a `BREAKING CHANGE:` footer; reference issues with `Closes #12` / `Refs #12`.
- **Record the change, never issue an instruction.** The subject and the bullets state what the commit contains and what it changes, as facts about the resulting state: "the auditor scans packages/web-styles/src again", "component-development describes the current layout", "ajout de quatorze feuilles de style". An imperative ("fix the auditor", "update AGENTS.md", "add thirteen families") reads as a task list handed to someone else and leaves the reader unable to tell whether the work was done — it is banned in the subject and in the bullets.
- **Bullets carry facts, not labels.** No "Why:", "Impact:", "API/impact:" or "Verification:" prefixes. Each bullet states a fact about the change: what changed, where, and its consequence when there is one.
- **Be detailed enough for another developer to follow the change without opening the diff**: the affected paths, the new or changed behaviour, and anything non-obvious.
- Stay factual. No filler, no restating the diff line by line, no invented intent.
- EN and FR must describe the **same** facts; French must be properly accented, not ASCII-folded.
- Write for the reader: a commit should read like a short changelog entry, not like a form.

## Skills used
`test-runner` (required), `test-coverage-audit`, plus any of `public-api-review`, `theme-integrity-audit`, `documentation-sync`, `playground-sync` when relevant.

## Failure conditions (abort)
- Unresolved conflicts, or a sensitive/generated file staged by accident.
- Unrelated changes mixed into the commit.
- Any mandatory validation fails (`pnpm verify:quick`).
- EN/FR sections disagree, or the message describes changes that are not in the diff.

## Validation criteria
- Only intended files staged; nothing unrelated.
- `pnpm verify:quick` green (or a documented, justified exception).
- Message matches the exact format, respects Conventional Commits.

## Report format
```
COMMIT
- files: <list>
- validations: <command → result>
- message:
  <the full message>
- pending (if any): <docs/demo/test items>
```

## Never
Generic filler text, invented features, "generated by AI" mentions, `--no-verify`, amending unrelated work, or imperative subjects and bullets that read as instructions.
